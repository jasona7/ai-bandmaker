## Adversarial spot-checks — fresh angles this pass

### Spot-check A: Focus-order trace on `/generate` after async DOM mutations

**Scenario:** A keyboard user has just clicked (Enter on) `#generateBtn` (`generate.html:26`). The handler `startGeneration()` runs (line 135), which calls `showProgress()` (line 136). `showProgress()` (lines 219-225) sets `#startGeneration` to `display:none`, unhides `#progressDisplay`, then calls `focusHeading('progressTitle')` (line 224) which programmatically focuses `#progressTitle` via the `tabindex="-1"` declared on line 35.

**Question:** What happens to focus during the window between `#startGeneration.style.display = 'none'` (line 220) and `focusHeading('progressTitle')` (line 224)?

**Trace:** The four DOM-mutation statements at lines 220-223 are synchronous. When `#startGeneration` is set to `display:none`, the `#generateBtn` inside it is removed from the accessibility tree and the layout. Most browsers (Chrome, Firefox, Safari) move focus to `<body>` when the focused element becomes `display:none`, but this is implementation-defined per HTML Living Standard §6.6.3 ("The currently focused area of a top-level traversable"). The subsequent `focusHeading('progressTitle')` runs in the same synchronous call stack before any browser re-paint or `focus` event dispatch, so the net observable effect is: focus moves directly from `#generateBtn` → `#progressTitle`. The intermediate "focus on `<body>`" state is never reachable by user keystrokes.

**ARIA implication:** Because `#progressDisplay` has `aria-live="polite"` (line 33) and `#progressTitle` is a `<h3 tabindex="-1">` inside it, the screen-reader experience is: (1) AT announces the focused heading text "Creating Your Band...", (2) the `aria-live` region begins polling-driven updates. This is the canonical "navigate-to-the-new-region after a state change" pattern from the WAI-ARIA Authoring Practices (§3.7 "Managing Focus").

**PASS.** No focus is lost; no error region is silently left without focus management. The four-region focus-management implementation at lines 211-217 (`focusHeading`) is correctly invoked from all four state-transition functions: `showProgress` (line 224), `showSuccess` (line 237), `showError` (line 246), and indirectly via `resetInterface` which does *not* call `focusHeading` (see next paragraph).

**Sub-question (fresh):** What about `resetInterface()` (lines 256-277)? It is called from `cancelGeneration` (line 253) and `generateAnotherBtn` (line 131). It re-shows `#startGeneration` and hides the other three regions but does **not** call `focusHeading`. After `cancelGeneration`, focus was on `#cancelBtn` (now inside the hidden `#progressDisplay`); after `generateAnotherBtn`, focus was on the now-hidden `#successDisplay > #generateAnotherBtn`. Browsers will move focus to `<body>` in both cases.

**Severity assessment:** This is technically a focus-management gap — after cancel/restart, the user must re-tab from the document start to reach the now-visible `#generateBtn`. However: (i) WCAG 2.4.3 (Focus Order) requires that focus order preserve meaning, not that programmatic focus be moved on every state change; (ii) WAI-ARIA APG §3.7 recommends but does not require focus management on every DOM transition; (iii) the surface is small (two buttons that lead to a screen with a single primary action). I would log this as **defensible polish** rather than a finding — adding `focusHeading('generateBtn')` to `resetInterface` would be a one-line improvement but the absence is not a WCAG AA violation. **Not promoted to a finding.**

### Spot-check C: `aria-live` region thrash at 1500 ms poll vs SR speech cadence

`generate.html:158`: `statusCheckInterval = setInterval(checkStatus, 1500);`
`generate.html:33`: `<div id="progressDisplay" ... aria-live="polite" aria-atomic="false">`
`generate.html:188-191`:
```js
document.getElementById('progressBarFill').textContent = '='.repeat(filled);
document.getElementById('progressBarEmpty').textContent = '-'.repeat(empty);
document.getElementById('progressPercent').textContent = ' ' + pct + '%';
document.getElementById('progressMessage').textContent = data.message || '';
```

Four `.textContent` assignments per 1500 ms tick. Typical screen-reader speech rate is 180-250 words per minute (≈ 350-500 ms per word). The text being assigned is short ("Creating band profile..." = 3 words, ≈ 1100 ms to speak).

**Failure mode if the message changes every tick:** The polite live region queues each new utterance after the current one completes. If the prose message changes faster than it can be spoken, the queue grows unboundedly until polling stops at `data.status === 'complete'`.

**Reality check against `app.py:139-203`:** The server-side messages are set at discrete progress thresholds: 10, 20, 35, 50, 60, 75, 90, 100. Between threshold transitions the message is *unchanged*. So most polling ticks return the **same** message text. The browser-side `textContent` assignment at line 191 *does* re-trigger an `aria-live` announcement on most screen readers even when the text is identical (because mutation observers fire regardless of content equality) — this is exactly N7 (carried Medium).

**Severity:** N7 already catalogues this; not a new finding. Confirming N7's MED-severity rationale: the announcement-spam is real but is not a WCAG AA conformance failure (Status Messages success criterion 4.1.3 requires that messages be announced, not that they be deduplicated). It is an annoyance, not a barrier.

**Sub-trace (fresh):** The four-textContent block also touches `progressBarFill`, `progressBarEmpty`, and `progressPercent` *inside* the `aria-live` region. These three elements are visual-only (ASCII bar art + percent). Should they be marked `aria-hidden="true"` to prevent screen readers from announcing them on every tick? Looking at `generate.html:39-42`:
```html
<div class="ascii-progress">
    <span style="color:#ffff00;">Progress: [</span><span id="progressBarFill" ...></span><span id="progressBarEmpty" ...></span><span style="color:#ffff00;"> ]</span>
    <span id="progressPercent" style="color:#ff00ff;"> 0%</span>
</div>
```

The `.ascii-progress` `<div>` is inside `#progressDisplay` (`aria-live="polite" aria-atomic="false"`). Because `aria-atomic="false"`, AT should announce **only the changed nodes** (not the whole region). The changed nodes are the inner `<span>`s `#progressBarFill`, `#progressBarEmpty`, `#progressPercent`. These announce as e.g. "equals equals equals dashes dashes dashes 15 percent" — verbose noise without semantic value.

**Should they be `aria-hidden="true"`?** Yes, this would be a polish improvement. But: (i) the prose message at `#progressMessage` ("Creating band profile...") *does* convey the same progress information in human language, (ii) the universal-selector animation kill at `style.css:465-471` does not address screen-reader output verbosity, only motion. This is a **new sub-Low** observation that overlaps with N9 (live region wraps too much) — log under N9 rather than a new ID.

**Not promoted to a new finding** (subsumed under existing N9). Polish-tier `aria-hidden="true"` would be a one-line fix on lines 39-42, deferred per the audit cadence.

### Spot-check F: `aria-busy` propriety on `#progressDisplay`

Yesterday's audit-2026-05-25 spot-check A briefly addressed `aria-busy` on `#generateBtn` (concluded redundant). Today's question is different: **should `#progressDisplay` itself have `aria-busy="true"` while generation is in flight?**

`aria-busy="true"` per ARIA 1.2 §6.4.1 indicates that an element and its subtree are being updated. AT may **defer** announcing changes until `aria-busy="false"` is set. The use case is exactly the live-region thrash described in spot-check C — set `aria-busy="true"` at `startGeneration()` (line 135), set `aria-busy="false"` immediately before the final state transition (success/error).

**Current behavior** (`generate.html:33`): `<div id="progressDisplay" ... aria-live="polite" aria-atomic="false">` — no `aria-busy`.

**Would adding `aria-busy` help?** It would suppress the per-tick "[X]" / "[>]" step-indicator updates (N6 problem) and the per-tick prose-message re-announcement (N7 problem) until generation completes — then the final state would announce as a coherent block. **But** this loses the per-step progress feedback that the `aria-live="polite"` design is intended to provide.

**Tradeoff:**
- `aria-busy="true"` throughout = no per-step updates, one coherent completion announcement → quiet but uninformative
- Current design = per-step updates with some thrash (N7) → noisy but informative
- The "right" answer per ARIA APG §6.5 "Live Region Recipes" is to keep `aria-live="polite"` *and* gate the updates client-side so they only fire on actual change boundaries (N7's recommended fix).

**Verdict:** Adding `aria-busy` would be a defensible alternative but not a clear improvement over the current `aria-live="polite"` design. The right fix is N7 (gate textContent on actual change), not adding `aria-busy`. **Not promoted to a finding.**
