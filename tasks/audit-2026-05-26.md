### Spot-check A: `SAFE_BAND_NAME` regex vs `**VelvetEchoes` orphan (re-verified WCAG 2.4.5 / Nielsen #9)

`app.py:21` defines `SAFE_BAND_NAME = re.compile(r'^[A-Za-z0-9_\-]+$')` and is checked in both `view_band()` (line 73) and `band_assets()` (line 85).

Replicated the gallery `glob.glob('*/home.html')` call and observed the on-disk orphan directory `**VelvetEchoes/` (carrying a `home.html`) is listed by `gallery()` because `glob.glob` does not apply the safe-name regex. Clicking through to `/band/**VelvetEchoes/` would then 404 via `abort(404)` because the regex correctly rejects the leading asterisks.

Three remediation options ranked:
1. **Filter at gallery render** — add `if SAFE_BAND_NAME.match(band_name)` inside the gallery loop in `app.py:58-65`. One-line fix, lowest-impact, idempotent with the existing regex.
2. **Rename the orphan directory** — `mv '**VelvetEchoes' VelvetEchoes` (or similar). Externalising; doesn't fix the class of bug.
3. **Custom 404 template** (Nielsen #9 recovery path) — independent of this orphan; tracked separately in 2026-05-25 spot-check C as a polish gap.

WCAG analysis: 2.4.5 (Multiple Ways, AA) is satisfied at the site level (nav bar provides alternate paths). The orphan-row → 404 dead-end is a Nielsen #9 (recognise/recover from errors) gap, not a WCAG failure.

**Not a finding.** This is the carry-over enumerated in audit-2026-05-12 ¶143 and audit-2026-05-14 ¶33 — observed today, severity unchanged. Documented for the record.

### Spot-check B: `viewBand()` redirect path-encoding trace (`templates/generate.html:279-283`)

`viewBand()`:
```js
window.location.href = '/band/' + encodeURIComponent(currentDirectory) + '/';
```

`currentDirectory` is set on line 171 from `data.directory`, which originates server-side from `create_project_directory()` (`createAct.py:642-658`). That function takes `band_name`, applies `''.join(word.capitalize() for word in band_name.split())` (line 644), and if the result already exists, appends a counter (`f"{directory_name}{counter}"`, line 648). The resulting directory name is **CamelCase ASCII alphanumerics with an optional trailing digit** — guaranteed to match `SAFE_BAND_NAME` (`^[A-Za-z0-9_\-]+$`) when constructed from English-alphabetic band names.

Edge case I checked: what if the AI returns a band name with **Unicode characters** (e.g. accented letters, CJK)? `.capitalize()` on a Unicode string returns Unicode; `''.join(...)` of Unicode chars produces a Unicode directory name; `os.makedirs(directory)` on a POSIX filesystem would create a non-ASCII directory; `SAFE_BAND_NAME` would then **reject** it on subsequent `/band/<name>/` access, producing a 404 immediately after the success screen.

However: this is **not** a JavaScript issue. `encodeURIComponent()` on the success path correctly encodes Unicode bytes to percent-escapes. The breakage happens server-side at the regex layer. This is a latent gap in the directory-creation contract — `create_project_directory` should sanitise to the same alphabet enforced by `SAFE_BAND_NAME`.

WCAG: 3.3.3 (Error Suggestion, AA) — applies to input forms, not URL routing. 2.5.3 (Label in Name, A) — n/a. Not a WCAG failure.

**Not promoted to a finding.** The Unicode-band-name path is a **latent reliability** issue that would manifest as "Band created successfully → click VIEW BAND PAGE → 404". Severity is LOW pending evidence that the OpenAI prompt at `createAct.py:61-79` ever produces Unicode band names; the prompt asks for "creative" but English-flavoured names, and seven generations in `tasks/` are all ASCII. Documented for the record; would escalate to MEDIUM if the prompt were ever broadened to non-English locales.

### Spot-check C: `:focus-visible` browser support fallback (`style.css:40-48`)

`style.css:40-48` defines the global focus indicator entirely via `:focus-visible`:
```css
a:focus-visible,
button:focus-visible,
.retro-button:focus-visible,
.retro-button-small:focus-visible,
.big-link:focus-visible,
[tabindex]:focus-visible {
    outline: 3px solid #ffff00;
    outline-offset: 2px;
}
```

Browser support audit:
- **Modern browsers** (Chrome 86+ from Oct 2020, Firefox 85+ from Jan 2021, Safari 15.4+ from Mar 2022): full support. **Estimated ~98% of current users.**
- **Older browsers without `:focus-visible`**: the entire selector group is invalidated per CSS error-recovery rules (CSS Selectors Level 3 — an unrecognised pseudo-class invalidates the selector). All focus styling is lost; user agents fall back to the browser-default focus ring (a 1-2px dotted or solid blue outline). **This is not "no indicator"** — it's a degraded indicator.

WCAG 2.4.7 (Focus Visible, AA) requires **a** focus indicator; it does not mandate that the focus indicator be the same in all browsers. Browser defaults satisfy 2.4.7 even if they don't match the design intent.

The selector list does **not** use comma-separated fallbacks (e.g. `a:focus, a:focus-visible`) which would cover legacy browsers with both styles. This is a deliberate choice — using `:focus` would re-introduce the mouse-click-shows-focus-ring anti-pattern. The design correctly trades off: legacy users get the browser default ring (still visible, still 2.4.7-conformant); modern users get the high-contrast `#ffff00` 3px outline.

WCAG 2.4.11 (Focus Not Obscured, AA) — newer 2.2 criterion — concerns whether the focused element is covered by other UI; not applicable to the indicator style.

**PASS.** No new finding.

### Spot-check D: `@media (prefers-reduced-motion: no-preference)` negative-condition gate (`createAct.py:427-435`)

Generated band CSS uses:
```css
@media (prefers-reduced-motion: no-preference) {
    h1.band-title {
        animation: bandTitlePulse 3s ease-in-out infinite;
    }
    @keyframes bandTitlePulse { ... }
}
```

This is the **inverted** gating pattern: animation is defined **only when** the user has not requested reduced motion. The default state (no animation) is the safe state. This is the recommended pattern from the WCAG 2.3.3 (Animation from Interactions, AAA) techniques and from MDN's `prefers-reduced-motion` guidance.

By contrast, the framework `style.css:457-472` uses the **positive** gate (`@media (prefers-reduced-motion: reduce)` then setting `animation: none`). Both patterns are conformant; the negative-gate pattern is strictly safer because it doesn't depend on the `reduce` query matching — if the browser cannot interpret the media query at all (very old browsers), the animation simply doesn't run.

Important nuance: `@keyframes bandTitlePulse` is **defined inside** the `@media (prefers-reduced-motion: no-preference)` block (line 431). Per CSS Animations Level 1, nested `@keyframes` inside `@media` are scoped to that media block — the keyframes are unavailable to any animation reference outside the media query. Since the only `animation:` property referring to `bandTitlePulse` is also inside the same media block, this is consistent.

WCAG 2.3.3 (Animation from Interactions, AAA) — the title pulse is autoplay, not interaction-triggered; not applicable. WCAG 2.2.2 (Pause, Stop, Hide, A) — `prefers-reduced-motion` honour satisfies the "user can stop motion" requirement.

**PASS.** No new finding.

### Spot-check E: `#bandPreview.innerHTML` self-XSS scope re-trace (M8 deferred — re-validated)

`templates/generate.html:233-236`:
```js
preview.innerHTML = '<p style="color:#00ffff; font-size:1.3em;">' +
    '~*~ ' + (data.band_name || 'Your Band') + ' ~*~</p>' +
    '<p style="color:#cccccc;">The fan page is ready!</p>';
```

Threat-modelling:
1. **Attacker controls `data.band_name`?** Only via prompt-injection of the OpenAI `gpt-4o` completion (`createAct.py:33-56`). The prompt template (`createAct.py:61-79`) is fixed; the user does not input any free text.
2. **Can a malicious AI completion inject script?** In theory yes — if the model output contained `<img src=x onerror=alert(1)>` as the band name, that string would land in `data.band_name` and then in `innerHTML`. The format-validation regex (`createAct.py:86`) only captures the line after `"Band Name:"`; it does not sanitise.
3. **What's the blast radius?** The victim is the same user who clicked Generate. Same-origin, same-session, self-inflicted. No cross-user XSS because each user runs their own generation.
4. **Is this WCAG-relevant?** No. WCAG does not address XSS.
5. **Is this security-relevant?** Yes, defense-in-depth — but the threat model (attacker-controlled OpenAI output reaching the user's own browser) is fragile and requires either (a) compromised OpenAI account or (b) prompt-engineering an adversarial completion. Severity is **MEDIUM**, already carried as M8.

Fix template (one-liner Edit when M8 is addressed):
```js
preview.textContent = '';
var titleP = document.createElement('p');
titleP.style.color = '#00ffff';
titleP.style.fontSize = '1.3em';
titleP.textContent = '~*~ ' + (data.band_name || 'Your Band') + ' ~*~';
var readyP = document.createElement('p');
readyP.style.color = '#cccccc';
readyP.textContent = 'The fan page is ready!';
preview.appendChild(titleP);
preview.appendChild(readyP);
```

**Not escalated.** Severity unchanged (MEDIUM). No remediation this pass — M8 remains deferred per the project's audit cadence.

### Spot-check F: `fetch().catch` reachability under non-JSON server response (`templates/generate.html:138-154, 161-180`)

`fetch('/api/generate', ...).then(response => response.json())` — if `/api/generate` returned a non-JSON body (e.g. an HTML error page from a Flask 500 with `DEBUG=True`), `response.json()` rejects with a `SyntaxError`, which propagates to the `.catch` handler (line 151). The catch calls `showError('Failed to start generation. Please try again.')` — which sets `aria-live="assertive"` on `#errorDisplay` (line 109) and focuses `#errorTitle` (line 246).

Cross-checked the alert vs assertive vs polite semantics:
- `role="alert"` on `#errorDisplay` (line 109) — `alert` has an **implicit** `aria-live="assertive"` and `aria-atomic="true"`.
- The explicit `aria-live="assertive"` on the same element is **redundant but harmless** (ARIA 1.2 §4.4 — explicit live-region attributes on a role that implicitly defines them produce no conflict).
- `focusHeading('errorTitle')` moves keyboard/SR focus to the alert heading after the assertive announcement — belt-and-braces UX.

WCAG 3.3.1 (Error Identification, A) — the error message is text, identifiable. PASS. WCAG 4.1.3 (Status Messages, AA) — assertive live region announces without focus change. PASS.

The status-check path (line 178-180) only `console.error`s and does not call `showError()`. If polling rejects (e.g. transient network blip), the user sees the progress bar stall but receives no on-screen feedback. This is the **N10 LOW carry-over** (failing step invisible to user). Reconfirmed today; severity unchanged.

**PASS at AA.** No new finding.
