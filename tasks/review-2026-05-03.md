## NEW Findings (2026-05-03 audit)

This pass found NO CRITICAL or HIGH issues. All new findings are MEDIUM or LOW. Per task instructions, these are logged and deferred (no code changes made).

### [MEDIUM] N5 — Progress-steps table column header is the literal "?"
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:46`
**Issue:** The first column of the live progress table has `<th scope="col">?</th>`. Screen-reader output is "Question mark, column header" for every cell in that column ("Question mark: dot dot dot. Step: Creating Profile"). The character is a visual placeholder for the dynamic step status (`...` → `[>]` → `[X]`), but as accessible-name content it conveys no meaning and creates confusing audio output. WCAG 1.3.1 (Info and Relationships, Level A) — the column header should describe the column's purpose.
**Fix (deferred):** Change the cell to `<th scope="col" aria-label="Status"><span aria-hidden="true">?</span></th>`. The visible glyph stays, but assistive tech now hears "Status".

### [MEDIUM] N6 — Step-indicator state changes are not announced to screen-reader users
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:183-209` (`updateProgress`)
**Issue:** The seven step rows update independently (`...` → `[>]` → `[X]`). The parent `#progressDisplay` has `aria-live="polite"`, but it also contains `#progressMessage` — which itself changes on every poll (every 1.5s). The rapidly-changing message text is what gets announced; the cell glyph changes are mostly buried. A screen-reader user gets no clear "Step 3 complete" notification, only the running prose message. This is a UX completeness issue, not a hard WCAG failure (the prose status message is technically sufficient). WCAG 4.1.3 (Status Messages, Level AA) is satisfied at the page level.
**Fix (deferred):** Either (a) add a separate `aria-live="polite"` `sr-only` announcer that is updated only when a step transitions to "[X]" with text like "Step 3 of 7 complete: Writing backstory", or (b) accept the current behaviour as adequate and document the rationale.

### [MEDIUM] N7 — Polling interval announces the same prose message many times
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:158, 183-191`
**Issue:** The status poller fires every 1.5s. Each tick rewrites `#progressMessage.textContent` even when the underlying server-side message has not changed (e.g. several polls all return "Writing band backstory..."). Because `#progressDisplay` is `aria-live="polite"`, some screen readers will queue a re-announcement on every textContent assignment, creating speech spam. WCAG 4.1.3 best-practice violation (status messages should be discrete, not continuous).
**Fix (deferred):** Cache the previous `data.message` value in a closure-scoped variable and only update `progressMessage.textContent` when it actually changes.

### [MEDIUM] N8 — `cancelGeneration()` does not tell the server to stop
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:249-254` and `app.py:90-122` (no cancel endpoint)
**Issue:** The "[ CANCEL ]" button only clears the client-side polling interval; the background `generate_band_async` thread keeps running, calls Anthropic + OpenAI APIs, writes a directory, and saves a `home.html`. Cost and disk impact for the user; UX expectation violated (button labelled "CANCEL" implies cancellation). Not an accessibility issue, but a UX truth-in-labelling issue (Nielsen heuristic #2: Match between system and the real world).
**Fix (deferred):** Either (a) add `POST /api/cancel/<generation_id>` that sets a `cancelled` flag the worker checks at each step boundary, or (b) re-label the button "[ HIDE ]" / "[ DISMISS ]" so the label matches the actual behaviour.

### [LOW] N9 — `#progressDisplay` `aria-live` region wraps a large amount of static markup
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:33-85`
**Issue:** The whole progress retro-box (heading, table of seven rows, ASCII bar, cancel button) lives inside the `aria-live="polite"` region. When the JS updates a single `step-indicator` cell or the percent text, some screen readers re-announce surrounding context. Best practice: keep `aria-live` regions as small as the actual changing content.
**Fix (deferred):** Move `aria-live="polite"` from `#progressDisplay` down onto a small `<p>` (e.g. `#progressMessage`), and let the heading + table + buttons be regular static markup.

### [LOW] N10 — Step labels in the `step-row` cells are static; failure of one step is invisible
**File:** `/home/jalloway/projects/ai-bandmaker/templates/generate.html:49-77`
**Issue:** When the backend hits an error mid-flow (e.g. DALL-E rate limit at step 6), the JS swaps to `#errorDisplay` and the partially-completed progress table is hidden. The user does not see *which* step failed. Minor diagnostic-value loss; not user-blocking.
**Fix (deferred):** On error, leave the progress table visible, mark the failing step `[!]` in red, and show the error message below it.

### [LOW] N11 — Generated band page nav uses pipe `|` separators only (same pattern as global nav)
**File:** `/home/jalloway/projects/ai-bandmaker/createAct.py:556-562`
**Issue:** The five in-page nav links (`#backstory | #photo | #members | #discography | #guestbook`) inherit the `.nav-bar a { margin: 0 5px; }` rule local to the generated page (lines 525-527). No `padding`, no `display: inline-block`, so touch-target height is ~21px — same WCAG 2.5.8 issue as N2 from yesterday's audit, but on the generated page CSS (which is a separate copy from `static/css/style.css`). Severity reduced because the generated page is supplementary content (not the app shell), but it is the same defect.
**Fix (deferred):** Add `display: inline-block; padding: 6px 8px;` to `.nav-bar a` inside `create_html_content`.

### [LOW] N12 — `body` font-family includes `cursive` as a generic-family fallback
**File:** `/home/jalloway/projects/ai-bandmaker/static/css/style.css:67` and `/home/jalloway/projects/ai-bandmaker/createAct.py:387`
**Issue:** `font-family: 'Comic Sans MS', 'Trebuchet MS', 'Arial', cursive, sans-serif;` mixes a specific cursive font with `cursive` and then `sans-serif`. If Comic Sans is unavailable on (e.g.) a Linux box without msttcorefonts, the chain falls through to `Trebuchet MS` and `Arial` (both sans-serif), but a fontconfig system that resolves `cursive` before reaching `sans-serif` may render the page in a hard-to-read decorative font. Cosmetic / readability concern; not a hard failure.
**Fix (deferred):** Either drop `cursive` and rely on the sans-serif chain, or move `cursive` to last position so `sans-serif` is preferred.

### [LOW] N13 — `<hr>` `noshade` and `size` attributes are obsolete in HTML5
**Files:**
- `/home/jalloway/projects/ai-bandmaker/templates/index.html:8,22,79,104`
- `/home/jalloway/projects/ai-bandmaker/templates/generate.html:7`
- `/home/jalloway/projects/ai-bandmaker/templates/gallery.html:7`
- `/home/jalloway/projects/ai-bandmaker/createAct.py:566,573,583,590,595`

**Issue:** `noshade` and `size="2"` on `<hr>` are non-conforming in HTML5. Browsers ignore them; the validator complains. Aesthetically intentional (90s vibe), but a pure HTML5 validator will flag them. (Same family as L14 in the prior review — already deferred there.)
**Fix (deferred):** Remove the attributes; the CSS already controls hr appearance.
