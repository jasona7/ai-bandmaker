## Adversarial spot-checks — fresh angles, not a copy of yesterday's

I deliberately rotated the spot-check angles so I am not just re-doing yesterday's pass.

1. **Body-background gradient dots vs. cyan link contrast.** Body has `background-image` with `radial-gradient(circle, #ffffff 0.5px, transparent 0.5px)` at `120px 120px` spacing plus a finer dotgrid at `80px 80px`. Cyan link `#00ffff` text against `#000022` body — calculated luminance ratio ~16.3:1 (AAA pass). But could a 0.5px white dot land behind link text and locally lower contrast against the cyan glyph? Mathematically yes, but the dot is sub-pixel, anti-aliased to near-transparent, and statistically covers <0.001% of a link-sized rectangle. Not a WCAG 1.4.3 violation — the spec evaluates against the "predominant" background. **PASS.**

2. **Live-region announcements with `display:none` → `display:block` transitions.** `#progressDisplay` and `#successDisplay` both declare `aria-live="polite"` and start hidden via inline `style="display:none"`. Some SR/browser combinations (older NVDA + Firefox specifically) have historically been inconsistent about announcing live-region content that was already in the DOM but only became visible on toggling display. Current code mitigates by calling `focusHeading()` immediately after showing the region (`generate.html:224,237,246`) — moving focus into the region forces the SR to read it. This is the correct pattern per WAI-ARIA Authoring Practices §8.5. The remaining "live region too broad" concern is logged as N9. **PASS.**

3. **`encodeURIComponent` on directory name in `viewBand()` — but what about path-segment-safe chars?** `templates/generate.html:281` builds `/band/' + encodeURIComponent(currentDirectory) + '/'`. `encodeURIComponent` does NOT escape `!*'()` per RFC 3986 but DOES escape `/`. Since `currentDirectory` is server-built by `create_project_directory()` which does `''.join(word.capitalize() for word in band_name.split())`, the directory is alphanumeric-only **only if the band name is alphanumeric+whitespace**. If OpenAI returns "Sigur Rós" or "AC/DC" the directory could contain accented characters or `/`. `encodeURIComponent` would percent-encode them, but then `SAFE_BAND_NAME` regex (`app.py:21` — `^[A-Za-z0-9_\-]+$`) would 404 the result. That's a UX bug (user clicks "View Band" → 404) but the threat model is server-validated-input-rejecting-its-own-output, not user-facing security. No CRITICAL/HIGH. Worth logging if reproducible, but practically rare and self-contained. **No new finding (latent edge case, deferred).**

4. **`<title>` injection vector — could band name break `<head>` parsing?** `createAct.py:381` interpolates `~*~ {band_name} ~*~ Official Fan Page ~*~` into `<title>`. If `band_name` contained `</title>` followed by markup, the head could be exploited. Practical risk: low (OpenAI gpt-4o doesn't emit malformed band names), but the right fix is `html.escape()`. This is the M8-sibling XSS surface, **already explicitly logged** at `tasks/review.md` (carry-over). **No new finding (already tracked).**

5. **`.gallery-thumb` `object-fit: cover` may hide faces.** `gallery.html:24` shows DALL-E band photo at 90x90 (desktop) / 60x60 (mobile), `object-fit: cover` (per `style.css:392`). DALL-E photos are square-ish, so cropping is minor. Not a WCAG violation; alt text "Promotional photo of {band.name}" carries the information for SR users. Could a 60x60 thumb meet 2.5.8 tap target? The thumb is wrapped in nothing — it's not a link itself; the `[ VIEW ]` button next to it is the link, with `min-height: 32px`. Adjacent column also has a link on the band name. So thumb is decorative-ish (no `alt=""` though — kept descriptive for SR). **PASS.**

6. **Duplicate-ID check across rendered pages.** Grepped all `id="` occurrences. Confirmed no duplicates within any single rendered template. The pre-generated band pages in `MoonlitReverie/`, `TheVelvetEchoes/`, `EchoesOfTheMirage/`, etc. were produced by an OLDER `createAct.py` and use IDs `backstory`, `members`, `discography` only (no `photo`, `guestbook`); they don't share IDs with framework templates because they're standalone documents served as-is. **PASS — no duplicates.**

7. **Drift between old served band pages and current generator output.** Existing band directories contain `home.html` files produced before the current generator. Their structure (CSS classes, ID set, ARIA usage) differs from what `create_html_content()` emits today. Visually, this is a content drift, not a code drift — those static HTML files are immutable deliverables of past generations. Not a finding against the current source tree; flagged here only to acknowledge the inconsistency a real user would notice if browsing the gallery: old bands look slightly different from newly-generated ones. **No new finding (informational only).**
