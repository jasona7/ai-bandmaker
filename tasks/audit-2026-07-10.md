## HIGH

### H4 — A generation can hang forever at 0% with no error and no recovery ✅ FIXED

**Files:** `app.py:27-38` (prune), `app.py:141-217` (worker), `app.py:130-138` (`api_status`),
`templates/generate.html:166-186` (`checkStatus`)
**WCAG:** 3.3.1 Error Identification (A) — a failure occurs and is never identified to the user.
**Previously logged as:** M10 + M3 + M6, three separate MEDIUMs, unfixed since 2026-07-05.

This is the same user outcome H2 was rated HIGH for: **the app's single primary task dead-ends,
silently.** Reproduced end-to-end, not inferred:

1. `cleanup_old_generations` popped any entry older than 60 min **with no check for whether that
   generation was still running** (`app.py:34-36`). It fires on every `POST /api/generate`.
2. The stranded worker's next `generation_status[generation_id].update(...)` raised `KeyError`.
3. The `except Exception` handler at `app.py:213` performed **the same subscript that had just
   failed** — raising a second `KeyError` while handling the first. **The worker thread died
   unhandled.** No `error` status was ever written.
4. `api_status` then returned `not_found`. `checkStatus` branched only on `complete` and `error`,
   so **`not_found` had no handler**: the poller ran forever at 1.5s intervals.

Observed before the fix:

```
entry survived prune: False
worker update raised KeyError: '20200101_000000'
  -> except-block ALSO raised KeyError  == THREAD DIES UNHANDLED
poll response: {'status':'not_found', 'progress':0, 'message':'Generation not found'}
client branch taken: none -> {cleared:false, errorShown:null, progressPainted:"0%"}
```

The user sees the panel still titled "Creating Your Band…", the bar **reset to 0%**, and polling
forever. The well-built `errorDisplay` (`role="alert"`, `aria-live="assertive"`, focus move,
Retry button — `generate.html:114-122`) is **never reached**, because the one failure mode that
occurs in production routes through the one status value with no handler.

**The 60-minute race is not even the common trigger.** `app.py` runs with `debug=True`, so the
Werkzeug reloader **restarts the process on any file touch**, wiping the in-memory
`generation_status` dict. *Every* in-flight generation instantly becomes `not_found`. In a dev or
demo setting this is routine. Any crash or a second worker process does the same.

`M6` is the third face of the same defect: `generation_id` was
`datetime.now().strftime("%Y%m%d_%H%M%S")` — **one-second resolution**. Two POSTs in the same
second shared one id, one status dict and one output directory; both browsers then navigated to
the same band via `viewBand()` while the other band was orphaned.

**Fix applied (`app.py`, `templates/generate.html`):**
- `cleanup_old_generations` now prunes **only terminal** entries (`complete`/`error`) older than
  the cutoff. A running generation keeps its entry however old it is.
- All status writes go through a new `update_status()` helper that returns `False` on a missing
  key instead of raising. The `except` handler uses it too, so **the handler can no longer raise
  the exception it exists to report**.
- `generation_id` is now `uuid4().hex`. Because uuid keys are not time-ordered, the prune reads a
  stored `created_at` instead of comparing keys lexicographically.
- `api_status` returns an explicit public-field projection, so the internal `created_at` datetime
  is not serialized into the API response.
- All `generation_status` access is serialized under a `STATUS_LOCK`; it is written by worker
  threads and read by request threads, and the prune previously iterated the dict while request
  threads inserted into it.
- `checkStatus` gained a `not_found` branch: it stops the poller and routes to `showError()` with
  a recovery message, *before* `updateProgress` can repaint the bar to 0%.

**Verified:** 16/16 assertions pass — a 5-hour-old *running* generation survives the prune; old
terminal entries are still collected; `update_status` on a missing key returns `False` rather than
raising; the worker-plus-handler double-`KeyError` path no longer throws; 1000 uuids yield 0
collisions; `created_at` is withheld from `api_status`; unknown ids return `not_found`; the client
now takes `{cleared:true, errorShown:"…"}` on `not_found` while the `running`/`complete`/`error`
paths are unchanged; `/`, `/generate`, `/gallery` still 200 and traversal still 404s.

## MEDIUM

### M11 — Discography collapses to one mislabeled album with raw markdown in the title (NEW)

**File:** `createAct.py:226-256` (new-album test at `:237`)
**Impact:** One of the four features the UI explicitly advertises (`generate.html:21`, "Full
discography with albums and tracks") silently breaks.

The only thing that starts a new album is the literal case-insensitive prefix `album:` (`:237`).
GPT-4o routinely emits markdown instead (`### Album 1: "…"`). When it does, the first such line
becomes the title *verbatim*, and every subsequent album header matches neither branch at `:237`
nor the track branch at `:243` — so it is **silently dropped**, and its tracks are appended to the
first album.

Reproduced by running the real `generate_discography_info` against both response shapes:

```
COMPLIANT format  -> 3 albums, correct titles
MARKDOWN  format  -> 1 album
   title: '### Album 1: "Celestial Reverberations" (1973)'
   tracks (5): all 3 albums' tracks merged into one list
```

This has already shipped to disk: `EchoesOfTheMirage/home.html` carries 12 lines of raw `###`/`**`
artifacts, `MoonlitReverie` and `TheVelvetEchoes` 3 each. `esc()` correctly escapes them, so they
render as *literal visible* `### Album Title 1:` text.

**Fix:** normalize each line before the prefix test and broaden the trigger:
```python
stripped = re.sub(r'^[#*\s]+', '', line)
if re.match(r'(?i)^album[:\s]', stripped) or re.search(r'\(\d{4}\)\s*$', stripped):
    current_title = re.sub(r'(?i)^album[:\s]*', '', stripped).strip(' "*')
```
