## Adversarial spot-checks — fresh angles this pass

### Spot-check A: Numeric WCAG 1.4.3 contrast recomputation on the two most-suspect palette pairs

Rather than re-assert "palette unchanged," I recomputed the two pairs most likely to fail AA.

**Pair 1 — `.banner-tagline` (`#ff69b4` hotpink) on the banner gradient (`style.css:99`, darkest stop `#000033`, lightest `#000099`).** "Creating Fictional Bands Since 1996" (`base.html:22`) is normal-weight ~13 px text (`0.9em` of 14 px), so the AA threshold is 4.5:1.
- Relative luminance of `#ff69b4` ≈ 0.325.
- Against the *lightest* gradient stop `#000099` (L ≈ 0.028): contrast = (0.325 + 0.05) / (0.028 + 0.05) ≈ **4.79:1** → passes.
- Against the *darkest* stop `#000033` (L ≈ 0.0035): contrast ≈ **6.94:1** → passes.
The worst case (lightest background under the text) is 4.79:1, above the 4.5:1 AA floor. **PASS at AA.** (It would fail AAA's 7:1, but the palette is not held to AAA.) No finding.

**Pair 2 — `.nav-bar a` (`#00ff00` lime) on `#111122` (`style.css:135,142`).** Bold ~13 px (`0.95em`), AA threshold 4.5:1 (it is below the 18.66 px large-bold cutoff).
- L(`#00ff00`) ≈ 0.7152; L(`#111122`) ≈ 0.0088.
- Contrast = (0.7152 + 0.05) / (0.0088 + 0.05) ≈ **12.99:1** → comfortably passes AA and AAA. No finding.

**Pair 3 (bonus) — generated-page nav `.nav-bar a` inherits `a{color:c1}` where `c1` can be `#ff69b4` (palette 4) on `#111111` (`createAct.py:391,520`).** L(`#ff69b4`) ≈ 0.325 on L(`#111111`) ≈ 0.0075 → (0.325+0.05)/(0.0075+0.05) ≈ **6.5:1** → passes AA. The other three `c1` options (`#00ffff`, `#00ff00`, `#ffff00`) are all higher-luminance and pass by wider margins. No finding.

**Verdict: no contrast finding at AA.** The single closest call site-wide is the decorative hotpink tagline at 4.79:1, which clears the bar.

### Spot-check B: Double-announcement analysis of `role="alert"` + `aria-live="assertive"` on `#errorDisplay`

`generate.html:109`: `<div id="errorDisplay" style="display:none;" role="alert" aria-live="assertive">`.

`role="alert"` carries an *implicit* `aria-live="assertive"` and `aria-atomic="true"` per WAI-ARIA 1.2 §5.3.1. So the explicit `aria-live="assertive"` here is **redundant** — the two do not stack into a double announcement (a node has a single computed live-region politeness; specifying the same value the role already implies is a no-op, not a second live region). The genuinely interesting question is the *timing*: `showError()` (lines 240-247) first flips `#errorDisplay` from `display:none` to `block` (line 244), then sets `#errorMessage.textContent = message` (line 245), then calls `focusHeading('errorTitle')` (line 246).

- Because the element is inserted into the a11y tree (via un-hiding) **and** its subtree text changes in the same synchronous frame, a `role="alert"` region reliably announces its full text on most screen readers (NVDA/JAWS/VoiceOver). **PASS** — the error is announced.
- `focusHeading('errorTitle')` additionally moves focus to the `<h3 tabindex="-1">`, so the heading text ("!! ERROR !!") is *also* spoken as the focus lands. Net result: the alert text and the focused heading are both announced, in close succession. This is slightly redundant but not harmful and not a WCAG violation (4.1.3 Status Messages is satisfied; 2.4.3 Focus Order is satisfied).

**Sub-note:** the redundant explicit `aria-live="assertive"` on line 109 is cosmetic cruft (could be dropped since `role="alert"` implies it), but removing it changes nothing observable. **Not promoted to a finding** — polish-tier at most, and lower value than the existing N-series items.

### Spot-check D: WCAG 1.4.10 Reflow at 320 CSS px

Reflow (AA) requires no loss of content/function and no two-dimensional scrolling at 320 CSS px width. The `@media (max-width: 640px)` block (`style.css:481-506`) is the only responsive breakpoint.

- **`.page-wrapper`** drops to `padding: 5px 8px` (line 483) and `max-width: 800px` (line 90) is never the binding constraint below 320 px, so the wrapper shrinks to viewport width — no fixed min-width forcing horizontal scroll.
- **Tables** (`.info-table`, `.gallery-table`, `.progress-steps-table`) go to `width: 100%; font-size: 0.85em` (lines 490-495). None sets a `min-width`, so cells wrap. The `.info-table` third column ("What Happens" prose) reflows vertically. **Caveat traced:** the `.progress-steps-table` header `<th width="30">` (`generate.html:46`) and the ASCII progress bar (`.ascii-progress`, monospace, `generate.html:39-42`) are the two widest fixed-ish elements. The ASCII bar is 20 chars + "Progress: [ ] NNN%" ≈ 32 monospace chars at `1.1em`×0.85 ≈ ~10 px/char ≈ 320 px — right at the edge. At exactly 320 px it may induce a few px of horizontal scroll on the progress bar row. This is a **known transient** (only visible during generation) and is bounded to the ASCII-art bar, whose semantic content is duplicated by `#progressMessage` prose. Borderline, but I judge it **does not rise to a 1.4.10 failure** because the bar is decorative (the `aria-hidden` candidacy noted under N9) and the equivalent information is available in reflowing prose. Logging as an observation, not a finding.
- **`.feature-cell`** switches to `display:block; width:100%` (lines 497-500), stacking the three feature boxes vertically. **PASS.**
- **`.gallery-thumb`** shrinks 90 px → 60 px (lines 502-505), keeping the gallery row within width. **PASS.**

**Verdict: PASS at AA**, with one borderline observation on the transient ASCII progress bar at exactly 320 px (subsumed under N9's aria-hidden recommendation; not a new finding).

### Spot-check E: `viewBand()` URL construction & orphan-directory 404 trace

`generate.html:279-283`: `viewBand()` does `window.location.href = '/band/' + encodeURIComponent(currentDirectory) + '/'`, where `currentDirectory = data.directory` (`checkStatus`, line 171) = `output_dir` from `create_project_directory` (`app.py:154-155`).

- `create_project_directory` (`createAct.py:642-658`) builds the directory as `''.join(word.capitalize() for word in band_name.split())` — it **does not** strip characters outside the `SAFE_BAND_NAME` alphabet (`[A-Za-z0-9_\-]`). If the AI emits a band name containing, e.g., `&`, `/`, or an accented letter, that character survives into the directory name and thus into `currentDirectory`.
- `view_band` (`app.py:70-79`) then rejects it: `SAFE_BAND_NAME.match(band_name)` fails → `abort(404)`. So the freshly-generated band 404s on "VIEW BAND PAGE", and the same band appears in the gallery (`gallery()` globs `*/home.html`) with a link that also 404s.

This is a **functional/robustness defect**, not a UX/a11y/WCAG-blocking one, and it depends on the AI emitting an out-of-alphabet character (uncommon but possible). It has been standing in the "Observations" ledger as *"`create_project_directory` does not sanitise to the `SAFE_BAND_NAME` alphabet"* and *"`**VelvetEchoes` orphan listed in gallery but 404s on click."* **Not promoted to Critical/High** — it is outside the WCAG-blocking bar this run fixes, and the graceful-degradation path (a plain-text 404) does not break the page the user is on. Remains an observation. (A clean fix would sanitise the directory to the `SAFE_BAND_NAME` alphabet at creation time in `create_project_directory`.)

### Spot-check F: `retro-button-small` touch-target measurement (gallery `[ VIEW ]`)

The gallery `[ VIEW ]` control is `<a class="retro-button-small">` (`gallery.html:36`). WCAG 2.5.8 (Target Size, Minimum, AA) requires ≥ 24×24 CSS px (or adequate spacing).

`style.css:306-319`: `.retro-button-small { padding: 8px 16px; min-height: 32px; display: inline-block; line-height: 1.2; font-size: 0.9em; }`.
- Height: `min-height: 32px` alone satisfies the 24 px floor; with `padding: 8px` top+bottom the rendered box is comfortably ≥ 32 px tall.
- Width: `padding: 16px` left+right around "[ VIEW ]" (~7 chars at ~7 px) ≈ 32 + 49 ≈ 80 px wide.
- **PASS at 2.5.8** (≥ 24×24). This matches the N2/N15 nav-link fixes and confirms the gallery's per-row action control is adequately sized on touch. No finding.
