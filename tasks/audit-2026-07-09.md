### H1 — HTML escaping in `create_html_content` → **HOLDS**

Ran `create_html_content` with hostile input in every model-controlled field (band name `Sun & Moon "Choir" <Live>`, `<script>alert(1)</script>` as style, `<img src=x onerror=alert(1)>` in the backstory, `<b>`/quote-injection in member name/instrument/bio, `<hits>`/`<track1>` as album and track titles), then parsed the output with `html.parser`:

```
INJECTED ELEMENTS: NONE
ALT ATTR: 'Promotional photo of Sun & Moon "Choir" <Live>'   (one intact attribute value)
raw <script> in source: False
injected onerror img:   False
```

The `alt` attribute survives as a single value rather than truncating at the first quote. All 13 interpolation sites route through `esc()` (`html.escape(..., quote=True)`) or `slugify_band_name()`. The only unescaped interpolations are fixed color literals, an integer visitor count, and `current_year`. **No injection path remains.**

### H3 — `aria-live` flood on poll → **HOLDS**

Markup assertions confirm `#progressDisplay` is no longer a live region; one dedicated `#progressStatus` (`role="status"`, `aria-live="polite"`, `aria-atomic="true"`) carries the message; all 7 `.step-indicator` cells are `aria-hidden="true"` with `.sr-only` text status alternatives; the `<th>?</th>` now has an `.sr-only` "Status" label. Re-implementing the DOM contract with a write-counting `textContent` setter: **13 identical 35% polls → 1 live-region write**; a real change to 50% → 2. Matches the claim.

## New findings

### M10 — pruned status entry kills the worker thread, and the error handler dies too (NEW, reproduced)

**File:** `app.py:27-38` (`cleanup_old_generations`) ←→ `app.py:141-217` (`generate_band_async`)

`cleanup_old_generations()` pops any `generation_status` key older than 60 minutes. It does not check whether that generation is still *running*. A generation that outlives 60 minutes (a slow DALL-E call, a retry storm) has its status entry pruned the moment any other user POSTs `/api/generate`. The worker thread then does `generation_status[generation_id].update(...)` on a key that no longer exists:

```
entry survived prune: False
worker update raised KeyError: '20200101_000000'
...and the except-block ALSO raises KeyError -> thread dies unhandled
```

The `except Exception` handler at `app.py:211` performs the *same* subscript, so it raises a second `KeyError` while handling the first. The thread dies unhandled, no band page is written, and — compounding with **M3** — the browser polls `not_found` forever at whatever percentage it last saw. The user watches a permanently frozen progress bar.

**Severity: MEDIUM, not HIGH.** It requires a >60-minute generation concurrent with another request. Real and reproducible, but not on the happy path. Fix would be `generation_status.get(gid, {}).update(...)`, or exclude non-terminal statuses from the prune.

### L14 — generated band page has no `<main>` landmark (NEW)

**File:** `createAct.py:create_html_content`

The standalone served band page — the app's actual product — is structured `<header role="banner">` → `<nav>` → bare `<h2>` sections inside `.page-wrapper`, with no `<main>` wrapping the primary content and no skip link. The prior report's "skip link + landmarks verified clean" covers the *app templates* via `base.html`; the generated page inherits none of that. WCAG 1.3.1 best-practice gap. LOW because the page is single-purpose and fully navigable.

`tasks/audit-2026-07-08.md` M2 suggests replacing `.step-indicator`'s `#666666` with `#8a8a99`, quoting "≈4.7:1". Recomputed from sRGB relative luminance:

| Pair | Actual |
|------|--------|
| `#666666` on `#0a0a1a` (current) | **3.414:1** — fails AA |
| `#8a8a99` on `#0a0a1a` (suggested) | **5.765:1** — not 4.7 |
| `#333333` on `#0a0a2a` (L1) | 1.525:1 |
| `#ff4444` on `#000066` (worst generated) | 5.170:1 |
| `#ff69b4` on `#000022` | 7.753:1 |

The suggested color over-satisfies AA rather than falling short, so the recommendation stands — but the number was wrong. Every other ratio in the prior report reproduced exactly to the decimal.
