## Adversarial spot-checks — async-state and form-semantics angles

### Spot-check A: Missing `aria-busy` / `disabled` on `#generateBtn` during in-flight `/api/generate` fetch (WCAG 4.1.3)

`generate.html:135-155` `startGeneration()`:
1. line 136: calls `showProgress()`, which sets `#startGeneration` to `display:none` (line 220) and `#progressDisplay` to `display:block` (line 221).
2. line 138: kicks off `fetch('/api/generate', { method: 'POST' })`.

The `#generateBtn` itself never receives `disabled` or `aria-busy="true"`. **However**, because `showProgress()` runs synchronously before `fetch()` settles, the button is already removed from the visible/interactable tree (`display:none` removes it from the accessibility tree and the tab cycle) by the time any AT could query it. The "busy" state is communicated by the `#progressDisplay` region (`aria-live="polite"` at line 33, programmatic focus to `#progressTitle` at line 224, and the visible "Creating Your Band..." heading) — which is the correct WAI-ARIA pattern for **region-level** state changes, distinct from per-control busy states.

WCAG 4.1.3 (Status Messages, AA) requires that status messages be programmatically determinable via role/property without receiving focus. The `aria-live="polite"` on `#progressDisplay` satisfies this. `aria-busy` on the button itself would be **redundant** given the region-level announcement and the fact that the button is no longer in the AT tree.

**PASS** under 4.1.3. No new finding.

### Spot-check B: Double-click / keyboard-repeat race on `#generateBtn` (`generate.html:128`)

Walked through the event-loop semantics:

1. User activates `#generateBtn` (click or Enter).
2. Click handler runs synchronously: `startGeneration()` → `showProgress()` (sets `#startGeneration` to `display:none`).
3. JavaScript is single-threaded; the next event in the queue cannot fire until the current handler returns.
4. By the time `fetch()` settles (network round-trip), `#startGeneration` (and thus `#generateBtn`) has been `display:none` for the entire interval.
5. A second `click` event queued during the fetch round-trip would target a `display:none` element — no handler fires.

The only theoretically-reachable race is if a user holds Enter with focus on the button before activation, generating a keyboard-repeat sequence. Browser keyboard repeat rate is ~30/sec (~33ms); the synchronous segment of `startGeneration()` is microseconds, and the first iteration's `showProgress()` removes the button from focus before the second `keydown` fires.

**Not a finding.** The architectural pattern (immediately hiding the trigger region on activation) is a defensible alternative to `disabled` attribute manipulation. No new finding.

### Spot-check C: Custom 404 error-page absence (`app.py:73-79, 85-86`)

`view_band()` and `band_assets()` both `abort(404)` when `SAFE_BAND_NAME.match()` fails. Additionally `view_band()` returns the plain string `"Band not found", 404` (line 79) when the path exists in regex but no `home.html` is on disk.

No `@app.errorhandler(404)` handler is registered (`grep -n 'errorhandler' app.py` returns no matches). Therefore Flask's default error page is served — an unstyled HTML document with the title "Not Found" and no navigation back to the site. This is a **UX** concern (dead-end for users hitting a broken gallery row, e.g. the `**VelvetEchoes` orphan) but not a WCAG violation:

- WCAG 2.4.5 (Multiple Ways, AA) is satisfied at the site level (nav bar, sitemap-like gallery, internal links) — a single missing 404 page does not break 2.4.5.
- WCAG 3.3.1 (Error Identification, A) applies to **input-form** errors, not generic 404s.

In Nielsen heuristic terms (#9, Help users recognise/recover from errors), the absence of a styled 404 is a polish gap. Severity is LOW: the failure mode is rare (404 only on broken gallery rows or hand-typed URLs), the recovery path is "press Back", and the dead-end is non-destructive.

**Not promoted to a finding this pass.** The orphan-gallery-row latent issue is already enumerated under the LOW deferral (audit-2026-05-12 ¶143, audit-2026-05-14 ¶33), and a custom 404 template is a separable polish item I'd raise only if the project added more pages or external linking. For now: observed, defensibly omitted.

### Spot-check D: `<table>` `<caption>` / `summary=` absence under WCAG 1.3.1 G115 (advisory)

Three data tables exist in the framework templates:

- `index.html:28` `<table class="info-table">` — six-row "How It Works" steps table.
- `gallery.html:14` `<table class="gallery-table">` — band list (one row per band).
- `generate.html:44` `<table class="progress-steps-table">` — seven-row step indicator.

None have `<caption>` or `summary=` attributes. `summary=` is deprecated in HTML5 (don't use it). `<caption>` is **advisory** under WCAG 1.3.1 (Technique H39 + H73 are "sufficient" techniques, not the only ones — and these tables are introduced by an adjacent `<h2>` section header which **also satisfies** the labelled-table requirement via WCAG Technique H51 + the immediately-preceding heading).

For each table:
- `info-table`: preceded by `<h2 class="section-header">~ How It Works ~</h2>` (`index.html:26`). Heading-as-label.
- `gallery-table`: preceded by `<h2>~ Band Gallery ~</h2>` plus an introductory `<p>` (`gallery.html:6,10`).
- `progress-steps-table`: inside `#progressDisplay` which is announced as a live region with `<h3 id="progressTitle">Creating Your Band...</h3>`.

All three tables have `<th scope="col">` headers (N3, N18 fixes) which is the load-bearing WCAG 1.3.1 H63 technique. The absence of `<caption>` is **not** a failure — heading + scoped column headers is a documented sufficient combination.

**PASS** under 1.3.1. No new finding. (`<caption>` would be a polish addition, not a remediation.)

### Spot-check E: `.nav-bar a` bounding-box height — numerical re-verification (WCAG 2.5.8 AA)

Recomputed end-to-end with the actual CSS values, no assumptions:

- Root `font-size: 14px` (`style.css:71`).
- `.nav-bar` `font-size: 0.95em` (`style.css:138`) → 14 × 0.95 = **13.30px**.
- Body `line-height: 1.5` (`style.css:70`) → content line height = 13.30 × 1.5 = **19.95px**.
- `.nav-bar a` `padding: 6px 8px` (`style.css:145`) → vertical padding 6 + 6 = **12px**.
- `display: inline-block` (`style.css:143`) → bounding box honours full content-line + padding.
- Total bounding box height = 19.95 + 12 = **31.95px**.

Touch-target rule WCAG 2.5.8 AA (24×24): **31.95 ≥ 24**, PASS with ~33% margin.

Horizontally, the shortest link text "Home" rendered bold at 13.30px ≈ ~30px text width + 16px horizontal padding ≈ 46px wide. PASS.

**PASS.** No new finding.

### Spot-check F: LVHA cascade-order verification (`style.css:74-87`)

`a`, `a:visited`, `a:hover`, `a:active` defined in that source order. CSS specificity is equal for all four (single pseudo-class), so source order resolves overrides. LVHA order means:

- `:visited` overrides default `a` colour for visited links.
- `:hover` overrides both `a` and `:visited` (so a visited link still goes yellow on hover, not purple-on-hover or stuck-purple).
- `:active` overrides all three during the brief mouse-down window.

`a` `#00ffff` → `a:visited` `#cc99ff` → `a:hover` `#ffff00` → `a:active` `#ff0000` all defined correctly. Verified that hovering a visited link produces yellow (not a colour collision). **PASS.**

### Spot-check G: `aria-current="page"` visual indicator (`base.html:28-30`) — observation, not finding

Active-page indicator is communicated to AT via `aria-current="page"` but no CSS rule targets `[aria-current="page"]`. Sighted users see no visual cue that they're on the current page — the bracket framing `[ Home ] | [ Generate a Band! ] | [ Band Gallery ]` is identical across all three links.

WCAG considerations:
- WCAG 2.4.8 (Location, **AAA** only) recommends a "you are here" indicator. Project targets **AA**, so this is not a conformance gap.
- WCAG 1.4.1 (Use of Color) does not apply — colour isn't the differentiator at all; nothing is.
- Heuristic literature (Nielsen #6, Recognition rather than recall) flags this as a wayfinding polish gap.

**Not promoted to a finding.** Project targets AA; documenting as an observation for the record. A two-line CSS addition (e.g. `.nav-bar a[aria-current="page"] { color: #ffff00; text-decoration: underline; }`) would close the AAA gap if/when the project adopts AAA targets.

### Spot-check H: `static/js/main.js` `prefers-reduced-motion` short-circuit (re-verified)

`main.js:5-10`: queries `window.matchMedia('(prefers-reduced-motion: reduce)').matches` and `return`s early, skipping the `setInterval` star-twinkle effect. Guard precedes the `try/catch` block (`main.js:14-25`), so even if `matchMedia` were undefined (Internet Explorer < 10), the JS error would be silently caught and the user would experience a static UI — fail-safe degradation.

WCAG 2.3.3 (Animation from Interactions, AAA) — about animation triggered by user interaction — is not relevant; the star twinkle is autoplay.
WCAG 2.2.2 (Pause, Stop, Hide, A) — `prefers-reduced-motion` is one of the two accepted mechanisms (the other being a per-element pause control).

**PASS.** No new finding.
