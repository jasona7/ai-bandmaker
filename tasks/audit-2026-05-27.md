## Adversarial spot-checks — new angles this pass

### Spot-check A: AI-text-to-HTML interpolation surface re-traced as **cross-user stored XSS** (re-categorisation of M8-sibling N19)

`createAct.py:376-626` constructs the band page via a single large f-string. I enumerated every f-string substitution that originates from AI output:

| Line | Expression | Sink |
|---|---|---|
| 381 | `{band_name}` | `<title>` text |
| 550 | `{band_name}` | `<h1 class="band-title">` text |
| 552 | `{style_name} | {genre1} / {genre2} | Est. {ref_year} | {nationality}` | `<p>` text |
| 570 | `{backstory}` | `<div class="backstory-box">` body |
| 577 | `{band_name}` | `<img alt="Promotional photo of {band_name}">` attribute value |
| 579 | `{', '.join(m.get('name', '') for m in band_members)}` | `<div class="photo-caption">` text |
| 600 | `{band_name.replace(' ', '').lower()}` | `mailto:` `href` attribute |
| 618, 619 | `{band_name}` | footer text |
| 347-351 (in `members_html`) | `{member.get('name')}`, `{member.get('instrument')}`, `{member.get('bio')}` | `<td>` text |
| 359, 364 (in `disco_html`) | `{track}` (in `<li>`), `{title}` (album title in `<td>`) | various `<td>`/`<li>` text |

**None are passed through `html.escape()`** — the file does not `import html` anywhere. A malicious AI completion containing `<script>...</script>`, `<img src=x onerror=...>`, or `</title>...<script>` would execute as HTML/JS in the rendered page.

**Critical distinction from M8** that the prior audits got *almost* right but the bookkeeping table dropped:
- M8 is **self-XSS** — the unsanitised band name lands in `bandPreview.innerHTML` only on the generating user's own success screen. No persistence; only their session.
- N19 is **stored, cross-user XSS** — the unsanitised text is written to disk by `save_html_to_file` (`createAct.py:630-639`) into the band's directory, then `gallery()` enumerates that directory via `glob.glob('*/home.html')` (`app.py:58-65`) and serves it to anyone who clicks through `/band/<name>/` from the public `/gallery` page (`app.py:70-79`).

Why MEDIUM, not HIGH?
- **Producer is OpenAI gpt-4o with internal-only prompts.** The user does not supply any free text to the model — the prompts at `createAct.py:61-79, 115-125, 143-152, 177-193` are entirely internal. There is no user-controlled prompt-injection vector.
- **The site has no auth, no sessions, no PII, no CSRF tokens.** XSS cannot escalate to account takeover, credential theft, or admin-impersonation because none of those exist.
- **Same-origin blast radius is limited to defacement + opening attacker-controlled URLs in the same tab.** No cross-origin amplification.
- The earlier audits (2026-05-21 ¶3, 2026-05-22 ¶4) reached the same MEDIUM verdict; my re-trace confirms that severity.

Why this is a discrete finding, not a duplicate of M8:
- M8's `templates/generate.html:233-236` fix (switch `innerHTML` → `textContent`) is a one-line client-side change.
- N19 requires a server-side `html.escape()` wrap on **every** interpolation point in `create_html_content` (12+ substitutions) and an `import html` at top of `createAct.py`. The two are independent edits in different files.

Bookkeeping fix this pass: N19 is now in the carried-over MEDIUM table below. **Not fixed this pass** (MEDIUM severity, deferred per the audit cadence; no Critical/High findings this pass).

### Spot-check B: `<title>` injection — does `</title>` in `band_name` allow head-injection?

`createAct.py:381`:
```
<title>~*~ {band_name} ~*~ Official Fan Page ~*~</title>
```

If `band_name` is exactly the string `Foo</title><script>alert(1)</script>`, the rendered head becomes:
```
<title>~*~ Foo</title><script>alert(1)</script> ~*~ Official Fan Page ~*~</title>
```

The HTML parser would close `<title>` at the **first** `</title>`, evaluate the injected `<script>`, then have a dangling `~*~ Official Fan Page ~*~</title>` in the body which would render as text. **This works** — `<title>` is a raw-text element whose only escape mechanism is `</title>`, and there is no upstream sanitisation.

This is a sub-case of N19 (broader interpolation surface), not a new finding. Severity remains MEDIUM under the same reasoning (AI producer, no auth, defacement-only).

### Spot-check C: `mailto:` href construction — `band_name.replace(' ', '').lower()`

`createAct.py:600`:
```
<a href="mailto:webmaster@{band_name.replace(' ', '').lower()}.geocities.com">
```

The `.replace(' ', '').lower()` removes spaces and lowercases. It does **not** percent-encode or remove HTML-significant characters. A `band_name` of `Foo"><script>alert(1)</script><a x="` would produce:
```
<a href="mailto:webmaster@foo"><script>alert(1)</script><a x=".geocities.com">
```

The `"` breaks out of the href attribute. Sub-case of N19; severity unchanged.

Even setting aside HTML-escaping, the resulting mailto address would not be a valid RFC 5321 local-part for many AI-generated band names (special characters, non-ASCII). This is L11 thematic — addressed only cosmetically.

### Spot-check D: gallery-row `hover` cue under keyboard-only navigation

`style.css:385-387`:
```css
.gallery-row:hover {
    background-color: #111133;
}
```

This is a `:hover` cue with no `:focus` companion. When a sighted keyboard user tabs through the gallery, the focus indicator on the `<a>` link inside the row appears (per `style.css:40-48` `:focus-visible` yellow outline), but the row itself does not get the slate-blue background.

WCAG 2.4.7 (Focus Visible, AA) requires *a* focus indicator, satisfied by the `:focus-visible` outline on the link. The row-level `:hover` cue is supplementary, not required. **PASS at AA.** Adding `.gallery-row:focus-within { background-color: #111133; }` would be a polish improvement (single-line CSS); not promoted to a finding because the per-link outline already exceeds the AA requirement.

### Spot-check E: `viewBand()` failure mode when `currentDirectory` is null

`templates/generate.html:279-283`:
```js
function viewBand() {
    if (currentDirectory) {
        window.location.href = '/band/' + encodeURIComponent(currentDirectory) + '/';
    }
}
```

If `currentDirectory` is null (e.g. the user somehow reaches the success display without `checkStatus` populating it — possible only via a race condition where the user clicks `VIEW BAND PAGE` before `data.status === 'complete'` lands), `viewBand()` silently does nothing.

Trace: `currentDirectory` is set on line 171 inside `if (data.status === 'complete')`; `showSuccess(data)` is called inside the same block on line 172. `showSuccess` is what unhides `#successDisplay` (line 230). The `viewBandBtn` (line 97-99) is inside `#successDisplay` which is hidden by default. So the button is only reachable after `currentDirectory` is set — the null-guard is defense-in-depth, not a real failure mode.

WCAG: not applicable (no error message because no error occurs). **PASS.** Silent no-op is preferable to a JS error or a `/band/null/` 404 redirect.

### Spot-check F: `extract_band_members` JSON-parse fallback bio re-enters the N19 surface

`createAct.py:169-172`:
```python
except (json.JSONDecodeError, KeyError) as e:
    logging.error(f"Error parsing band members JSON: {e}")
    # Fallback: return a minimal member list
    return [{"name": band_profile["Band Name"], "instrument": "various", "bio": "The band."}]
```

If the OpenAI response for member extraction is malformed JSON, the fallback uses `band_profile["Band Name"]` as the member's name. This re-enters `members_html` (`createAct.py:347-351`), which is interpolated unescaped into the generated HTML. **Same N19 surface, same severity.**

The fallback is well-intentioned (degrades gracefully rather than crashing), but it doubles the attack surface — now both `band_profile['Band Name']` and the AI's JSON-formatted members reach the page unsanitised. Fix is the same: `html.escape()` at every interpolation point covers this path too.

**Sub-case of N19; not a separate finding.**
