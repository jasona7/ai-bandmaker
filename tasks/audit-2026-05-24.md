## Adversarial spot-checks — interaction-flow angles

### Spot-check 1: WCAG 1.4.1 link-vs-surrounding-text contrast (F73)

WCAG Technique F73 fails interfaces where links are identified by **color alone** against surrounding text, with adjacent-text contrast below 3:1 and no other visual differentiator. I numerically recomputed the link-to-prose adjacent-text contrast for the two most exposed link surfaces:

- `.big-link` `#ffff00` adjacent to body text `#cccccc`: ratio ≈ **1.50:1** (below 3:1).
- `.nav-bar a` `#00ff00` adjacent to body text `#cccccc`: ratio ≈ **1.17:1** (below 3:1).

Both fall below the 3:1 colour-only threshold. **However**, F73 only applies when colour is the **sole** differentiator. Inspecting the rendered presentation:

- `.big-link` (`style.css:193-199`): `font-size: 1.2em; font-weight: bold; text-decoration: none`. The 1.2× scale + bold weight are independent non-colour cues → F73 does NOT apply.
- `.nav-bar a` (`style.css:141-147`): `display: inline-block; padding: 6px 8px; font-weight: bold; margin: 0 3px`, with `[ ... ]` bracket characters as static text in the template (`base.html:28-30`). The bracket framing + bold + inline-block presentation are independent non-colour cues → F73 does NOT apply.
- Body links (`style.css:74-77`): `text-decoration: underline` at rest — independent non-colour cue → F73 does NOT apply.

**PASS** under 1.4.1. No new finding.

### Spot-check 2: `a:hover { text-decoration: none }` (style.css:81-84) regression

Body links remove their underline on hover. This is a "negative differentiation" pattern — at rest the link has colour+underline, on hover it has colour-only. WCAG 1.4.1 applies to the **default** static presentation, not hover-transient states, so this is not a 1.4.1 failure. Some heuristic literature flags it as a discoverability concern (Nielsen) because hover hides an affordance, but the colour still changes (`#00ffff → #ffff00`, ratio change ≈ 14×→17×) and the cursor still indicates pointer. **Not a finding** — purely a style preference within the retro pastiche aesthetic.

### Spot-check 4: `glob('*/home.html')`-surfaced orphans (re-verification, directional)

The `**VelvetEchoes` directory on disk (`ls -la "/home/.../**VelvetEchoes"`: 8485-byte `home.html`, 2014283-byte `band_photo.jpg`, created 2025-04-30) is picked up by `glob.glob("*/home.html")` in `gallery()` (`app.py:58`) and rendered as a gallery row. The `re.sub(r'([A-Z])', r' \1', band_name).strip()` display transform turns `**VelvetEchoes` into `** Velvet Echoes`. Clicking "View" sends the user to `/band/**VelvetEchoes/` → `SAFE_BAND_NAME.match()` fails → `abort(404)`.

This is a **known LOW-severity latent UX issue**, characterised in `tasks/audit-2026-05-12.md:143` and `tasks/audit-2026-05-14.md:33`, and the design decision was: keep the regex strict (security-first), accept that pre-existing orphans render as broken-link gallery rows. The fail-safe behaviour (`abort(404)` rather than serving) is correct.

**Today's new angle:** would the app itself ever **create** such an orphan? `create_project_directory` (`createAct.py:642-658`) does `''.join(word.capitalize() for word in band_name.split())` — strips inner whitespace but does **not** strip punctuation. If the LLM returned `"M.I.A."` or `"AC/DC"` or `"*NSYNC"`, the directory could be created with characters that fail `SAFE_BAND_NAME`, producing the same broken-link symptom going forward. The OpenAI prompts (`createAct.py` `generate_band_profile`) ask for fictional band names without explicit constraint to alphanumerics, so this is a real residual risk — but it's the same latent finding already enumerated (per `tasks/audit-2026-05-17.md:32` spot-check 2) and the established disposition stays LOW: model prompts implicitly steer away, no new test data has exhibited the failure mode, and the security benefit of the strict regex outweighs the rare edge case. **Not promoted.** No new finding.

### Spot-check 5: `viewBand()` round-trip alphabet alignment (numerical)

`generate.html:281`: `window.location.href = '/band/' + encodeURIComponent(currentDirectory) + '/'`. I verified the alphabet alignment numerically:

- `SAFE_BAND_NAME = ^[A-Za-z0-9_\-]+$` accepts the 64-char alphabet `A-Z a-z 0-9 _ -`.
- JavaScript `encodeURIComponent` passes through unchanged: `A-Z a-z 0-9 - _ . ! ~ * ' ( )`.
- `SAFE_BAND_NAME`'s 64-char alphabet is a strict subset of `encodeURIComponent`'s 70-char passthrough alphabet → for any directory name the regex accepts, `encodeURIComponent` is the identity function, and the round-trip preserves the path exactly.

**PASS** — no encoding-induced 404. No new finding.
