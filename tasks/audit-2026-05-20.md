### New independent spot-checks this pass (not previously logged)

1. **Keyboard-only walk through `/generate` four state transitions.** Independent tab-order re-derivation:
   - State 1 (`#startGeneration` visible, other three siblings `display:none`): skip-link → 3 nav links → `#generateBtn`. Five tab stops.
   - State 2 (`#progressDisplay` visible): skip-link → 3 nav links → `#progressTitle` (programmatically focused by `focusHeading('progressTitle')` at `generate.html:224`, has `tabindex="-1"` so not in tab sequence but receives focus on state change) → `#cancelBtn`. The progress-steps-table contains no tabbable elements (only `<td>` text), so the single tab stop inside the panel is `#cancelBtn`. **No keyboard trap; no orphan focus.**
   - State 3 (`#successDisplay` visible): skip-link → 3 nav links → `#successTitle` (focused) → `#viewBandBtn` → `#generateAnotherBtn`. Three tab stops in panel.
   - State 4 (`#errorDisplay` visible): skip-link → 3 nav links → `#errorTitle` (focused) → `#retryBtn`. Two tab stops in panel.
   - All previous-state buttons are `display:none` so correctly removed from tab order (browsers exclude `display:none` from sequential focus navigation per HTML living-standard §6.6.3). **PASS.**

2. **`aria-atomic` value correctness on the three live regions in `generate.html`.**
   - `#progressDisplay` (line 33): `aria-live="polite" aria-atomic="false"` — correct, because the region wraps a lot of static labels plus a handful of `.textContent`-updated nodes (`#progressMessage`, `#progressBarFill`, `#progressBarEmpty`, `#progressPercent`, seven `.step-indicator` cells). With `aria-atomic="false"`, only changed nodes are announced, avoiding re-announcement of the surrounding scaffold. (This still has the N7 / N9 carry-over noise issue, but the atomicity value itself is correct.)
   - `#successDisplay` (line 88): `aria-live="polite" aria-atomic="true"` — correct, because this panel is shown only once on completion and its contents are a coherent unit users want spoken together (band name + readiness message).
   - `#errorDisplay` (line 109): `role="alert" aria-live="assertive"` — `role="alert"` already implies `aria-live="assertive"` and `aria-atomic="true"`, so the explicit `aria-live` is cosmetic redundancy. Not a violation; allowed by ARIA 1.2 §5.3.2. The error panel is coherent and should be spoken as a unit. **PASS.**

3. **`role="dialog"` / `aria-modal` independent grep.** Zero matches across `templates/`, `static/`, `app.py`, `createAct.py`. The four `/generate` state panels are sibling `<div>`s toggled by `display:none`, not modals. **No focus-trap risk** (Nielsen heuristic 3, user control and freedom — escape via keyboard or browser back button works at all four states).

4. **`<button>` vs `<a>` semantic correctness re-derived from scratch.**
   - `gallery.html:31` band-name link: navigates to `/band/<dir>/` → `<a>` correct (WCAG 4.1.2; right-click "open in new tab" works).
   - `gallery.html:36` `[ VIEW ]` styled-as-button link: also navigates to the same URL → `<a>` correct. (Styled to look like a button via `.retro-button-small` but exposes link semantics to AT.)
   - `index.html:69, 73` `big-link` and `gallery.html:48, 55` `big-link`: anchors that navigate → `<a>` correct.
   - `generate.html:26, 80, 113` `generateBtn`, `cancelBtn`, `retryBtn`: trigger JS state changes only → `<button>` correct.
   - `generate.html:97, 101` `viewBandBtn`, `generateAnotherBtn`: `viewBandBtn` does `window.location.href = ...` (navigation), but uses a `<button>` because the destination URL depends on JS state (`currentDirectory`). Defensible — could alternatively be a link whose `href` is updated on success, but the current approach is not a violation. `generateAnotherBtn` is a state-reset (no navigation) → `<button>` clearly correct. **PASS.**

5. **Viewport zoom-restriction grep.** Zero matches for `user-scalable=no`, `maximum-scale=1`, `maximum-scale=1.0` anywhere. WCAG 1.4.4 "Resize text" (AA) and 1.4.10 "Reflow" (AA) honoured — users can pinch-zoom freely on mobile. **PASS.**
